# Thinking 重复检测算法优化设计

> 待验证。调研业界方案后整理的优化方向，未实际修改代码。

## 问题

推理模型在 thinking 阶段会出现周期性复读（如"调免调免调免"），浪费 token 直到 max_tokens 耗尽。当前 `thinkingLoop.ts` 用精确字符串匹配检测，但存在两个不足：

1. **精确匹配脆弱**：`indexOf` 要求 100 字符完全一致，微小的空格/标点变化就漏检
2. **检测滞后**：`MIN_CHARS = 1000` 才启动检测，前面已浪费大量 token

用户截图中 think 内容是短语级重复（"调免"循环），当前算法应该在 p=2~3 的短周期路径命中，但如果重复单元前后有微小变化（如"调免 "vs"调免"），精确匹配会漏过。

## 业界方案调研

### 1. Step Code（当前）——检测后截断

- 短周期：末尾周期 p ∈ [1,30] 精确复读 ≥ 8 次
- 长重复：100 字符窗口在更早内容中 ≥ 5 次，平均间距 ≤ 200 字符
- 最小检测长度 1000 字符
- 命中后切断流，注入提示让模型重新回答

### 2. Claude Code / llama.cpp ——DRY 采样（源头预防）

- `--dry-multiplier 0.8`：DRY 乘数
- `--dry-base 1.75`：指数惩罚基准
- `--dry-allowed-length 2`：≤ 此长度不惩罚
- 公式：`penalty = multiplier × pow(base, seq_len - allowed_len)`
- 在采样时修改 logits，降低重复序列概率，从源头预防
- 序列断点：`\n`、`:`、`"`、`*` 会重置检测

### 3. Yuan3.0 Flash ——n-gram 重复率

- 每 1024 token 做一次检测
- 唯一字符 < 80% 时触发 -1.0 penalty

### 4. WordSaladChopper ——隐藏状态监控

- 以 `\n\n` 分段
- 连续 2 段被判定为"词语沙拉"就切断
- 需要访问模型隐藏状态，应用层无法实现

### 5. Gemini CLI ——块哈希

- 100 字符块做哈希
- 同一哈希出现 ≥ 3 次触发

### 6. Kimi Code ——步数限制

- 只有 `max_steps_per_turn`（步数级），无 think 内容级检测
- 社区反馈 K2.6 模型"过度思考"问题严重

## 优化方向

### 方向 A：归一化层（低成本，推荐先做）

在现有精确匹配前加一层归一化：

1. 去空格、去标点
2. 小写化（英文部分）
3. 在归一化文本上跑现有算法

效果：同一个短语无论中间有没有空格/标点变化，归一化后都是同一个字符串，精确匹配就能命中。

实现：在 `detect()` 入口处加 `const normalized = buf.replace(/\s+/g, '').toLowerCase()`，在归一化文本上跑检测，但 `sample` 仍取原始文本。

### 方向 B：n-gram 重复率（Yuan3.0 Flash 方案）

补充一条新的检测路径：

1. 取末尾 256 字符
2. 计算 2-gram 的重复率（重复 n-gram 数 / 总 n-gram 数）
3. 重复率 > 0.6 时判定为循环

这条路径不依赖精确匹配，对微小变化也敏感。

### 方向 C：降低 MIN_CHARS

从 1000 降到 600 或 400。前 600 字符通常是正常推理展开，但 600 之后的重复大概率是循环。

### 方向 D：采样干预（长期，需 API 支持）

如果 API 支持 logit bias 或 repetition penalty，可以在检测到早期循环信号时动态调整采样参数，从源头降低重复概率。这不是所有 API 都支持，作为长期方向记录。

## 推荐实施顺序

1. **方向 A（归一化）**：改动最小（~10 行），效果最直接，先做
2. **方向 B（n-gram 重复率）**：补充检测路径，~20 行
3. **方向 C（降 MIN_CHARS）**：改一个常量
4. 方向 D 暂不做，等 API 支持情况明确

## 验证方式

每步改完后跑 `thinkingLoop.test.ts`（如有）或新增测试用例：
- "调免 调免 调免"（带空格短语循环）
- "abc abc abc abc abc abc abc abc"（英文短语循环）
- 正常推理文本不误报
- 代码块/列表中的合理重复不误报
