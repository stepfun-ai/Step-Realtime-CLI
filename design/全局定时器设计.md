# 全局定时器设计思考

> 待用户拍板。分析三个方案的取舍。

## 现状

cron 任务存储在 cwd 对应的 store 里，由当前运行的 step-code 进程的 CronScheduler 管理：
- 每个 job 带创建者 sessionId
- /resume 后只恢复本 session 的 cron（sessionId 过滤，已修复跨 session 串台）
- 进程退出后 cron 停止，下次启动恢复

## 用户问题

> 全局定时器我不知道是否有用，但是这个全局定时器的使用的话这个是需要依赖至少有一个 step code 在后台运行才可以吧？

用户说对了。当前实现是**进程内定时器**——进程退出后定时器停止，下次启动恢复。不存在系统级的后台守护进程。

## 三个方案

### 方案 A：保持现状（session-scoped）

- cron 任务绑定到创建它的 session
- /resume 后恢复本 session 的 cron
- 进程退出后 cron 停止，下次启动恢复

**优点**：
- 简单，不会串台（已通过 sessionId 过滤修复）
- 不需要额外进程
- 行为可预测：关了 step-code 什么都不跑

**缺点**：
- session 被删了，cron 任务也丢了
- 不能跨 session 共享定时任务

**适合场景**：当前用户的使用模式——一个 step-code 进程管一个会话，定时任务跟着会话走。

### 方案 B：cwd-scoped

- cron 任务绑定到 cwd（工作目录），不绑定到 session
- 同一个 cwd 下的所有 session 共享 cron 任务
- 进程退出后 cron 停止，下次启动恢复（但恢复时不过滤 sessionId，恢复所有本 cwd 的）

**优点**：
- session 删了任务还在
- 同一个项目下的不同会话共享定时任务

**缺点**：
- 需要处理多个 step-code 进程同时管理同一 cwd 的 cron（可能重复触发）
- 比方案 A 复杂

**适合场景**：用户在不同 session 里对同一个项目设置了定时任务，希望不随 session 删除而丢失。

### 方案 C：全局（global）

- cron 任务不绑定到 cwd 或 session
- 需要至少有一个 step-code 进程在后台运行才能触发
- 所有 step-code 进程共享同一份全局 cron 表

**优点**：
- 最灵活，跨 cwd、跨 session
- 类似系统 cron 的体验

**缺点**：
- 最复杂：需要文件锁防止多进程重复触发、需要后台进程保活
- 如果所有 step-code 进程都关了，全局定时器就跑不了（用户已经指出了这一点）
- 实现成本高，ROI 低

## 推荐

**方案 A（保持现状）**。理由：
1. 用户当前的使用模式是单进程单会话，session-scoped 足够
2. 全局定时器需要后台守护进程，实现成本高且用户已经质疑其价值
3. 如果将来需要跨 session 共享，可以升级到方案 B（改动小）

## 如果选方案 B 的实现要点

1. store.load(cwd) 返回所有本 cwd 的 job（不过滤 sessionId）
2. 恢复时全部装回（不做 sessionId 过滤）
3. /cron list 显示所有本 cwd 的 job
4. /cron delete 可以删除任何本 cwd 的 job
5. 多进程竞争：用文件锁或 CronScheduler 内部的 tick 互斥（已有）
